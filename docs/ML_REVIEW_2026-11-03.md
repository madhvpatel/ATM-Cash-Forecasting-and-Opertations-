# ML Methodology Review — Cash Forecasting Models

**Date:** 3 November 2026
**Scope:** `live_portal/generate_portal_data.py` (portal models; byte-identical `.txt` models in `UI_2/` and `live_portal_v2/`), `replenishment_engine/forecaster.py` + `uncensoring.py` (replenishment engine), `simulated/maharashtra/run_rolling_origin.py` (backtest).
**Data:** 8 synthetic Maharashtra ATMs, 754 days (2024-09-01 → 2026-09-24). Everything below describes the simulator, not production.
**Method:** I read the code, then re-ran every model read-only, with outputs going to a scratch folder. No project files were changed.

---

## 1. Bottom line

| Question | Verdict |
| --- | --- |
| Is the accuracy figure trustworthy? | **No, as displayed.** The portal shows ~90% "accuracy" (10.0% WAPE for Strategy B), but that is measured on the 8-ATM *portfolio total*. Errors cancel across ATMs. Per-ATM-day WAPE is **18.2%**, and cash is loaded per ATM. |
| Data leakage? | **Yes, two leaks.** One is material: the replenishment engine trains on the test week (WAPE 15.5% looks better than the true 17.4%). The other is small: festival multipliers peek at in-window actuals. |
| Structural breaks? | **Not handled.** No change-point detection, recency weighting or trend term. A +30% level shift makes the static models under-forecast by ~19%. Only Strategy C adapts. |
| Exponential cash flows / scaling? | **The premise doesn't hold here** (skew 0.89, no exponential growth). Trees don't need feature scaling. The real problem is that trees **cannot extrapolate** beyond the levels they saw in training. |
| Erratic / non-linear anomalies? | **No anomaly treatment exists.** No outlier flag, no winsorising, no downtime model. Only the L1 loss gives robustness. 32 of 37 spike days are calendar-explained. The synthetic data contains **no** outages or drops, so this path is untested. |
| "Zero-shot cold start" (Strategy B, starred)? | **Not supported by evidence.** Leave-one-ATM-out WAPE is **27.9%** (vs 18.2% in-sample), with per-ATM bias up to **+49%**. |

The cleanest number in the repo is the rolling-origin backtest: **LightGBM 18.6% WAPE vs 21.1% seasonal benchmark** across 55 weekly origins. Use that as the reference. It is scored on observed `demand`, not `uncensored_demand`, so it is not directly comparable to the portal figures.

## 2. Accuracy as measured

Portal holdout: one 31-day window (25 Aug – 24 Sep 2026, which includes Ganesh Chaturthi), scored on `uncensored_demand`.

| Model | Per-ATM-day WAPE | Bias | Portfolio WAPE (what the UI shows) |
| --- | --- | --- | --- |
| Pure exogenous (terminal_id + calendar) | 18.0% | +4.0% | 9.7% |
| Strategy B — site profiler ⭐ | 18.2% | +3.2% | 10.0% |
| Strategy C — telemetry-adaptive | 20.4% | −6.9% | 11.1% |
| Strategy A — volume-normalised | 21.1% | +5.4% | 10.6% |
| LightGBM on censored target | 18.2% | +1.9% | — |
| Naive (last week) | 29.3% | −16.2% | — |

Issues with this evaluation:

- **Portfolio aggregation hides error.** `accuracy_pct = 1 − WAPE` is computed on daily sums across ATMs (`generate_portal_data.py:1093`). Over-forecasts at one ATM cancel under-forecasts at another. Report per-ATM-day WAPE as the headline figure.
- **Single origin.** One 31-day window, containing one mega-festival, is one sample. The rolling-origin protocol (55 origins) is the right design. Port the portal models into it.
- **Horizon mismatch.** The portal scores days 1–31 from a fixed cutoff, but replenishment is a 7-day decision. Day-25 accuracy does not matter for this week's indent.
- **Target is itself an estimate.** The portal scores against `uncensored_demand`, which a heuristic constructs (see §6). Part of the "error" is error in the target.

## 3. Data leakage

### 3.1 Replenishment engine trains on the test week — **HIGH**

`replenishment_engine/forecaster.py:152`

```python
train = df_feat[df_feat["cutoff_date"] < cutoff_date]
```

Each row is keyed by `cutoff_date` but carries a target up to 7 days later. Rows with cutoff `c−1 … c−6` have targets on `c+1 … c+6`, which are the very days being tested. That is **21 leaked rows per ATM per cutoff**.

| Split | WAPE (26 weekly origins × 8 ATMs) |
| --- | --- |
| As coded (leaky) | **15.5%** |
| Fixed: `target_date <= cutoff` | **17.4%** |

This inflates accuracy by ~2 points, or ~11% relative. `run_simulation.py:112` calls this path, so any replenishment cost or savings result from the engine inherits the leak. The previous review (27 Oct) flagged this split, and it is still unfixed.

**Fix:** `train = df_feat[df_feat["target_date"] <= cutoff_date]`. The rolling-origin script already does this correctly (`run_rolling_origin.py:563`, with an assertion).

### 3.2 Festival multipliers read in-window actuals — LOW (real, small)

`generate_portal_data.py:347-373`. `prior_festival_multiplier` is "the lift on the last occurrence of this festival key". It is computed over the **whole panel**, including the test window:

- `GANESH_PRE` spans two days. The second day's "prior" value is the first day's **actual test-window lift**.
- The site-type version sorts all ATMs of a site type by date. With multiple ATMs, a sibling's **same-day** actual would leak in. Today each site type has exactly one ATM, so this is latent.

Effect, measured by freezing the multipliers at the cutoff: festival-day WAPE goes from 26.6% to 27.6% and all-day WAPE from 18.0% to 18.2% (8 test rows affected).

**Fix:** compute multipliers from `panel[date <= cutoff]` only, then map them forward.

### 3.3 Latent / minor

- **Naive baseline fallback is the answer** (`generate_portal_data.py:613`): `dow_last_week.get(..., r["demand"])` falls back to the actual test value. It never fires today, because the 7-day window covers every weekday. It will fire if a terminal has missing days. The baseline is also built on observed `demand` and scored on `uncensored_demand`.
- **Engine "naive_last_week" is a constant, not seasonal naive** (`forecaster.py:160`): `lag_7` is anchored to the cutoff, not the target, so all 7 forecast days get the same value (208/208 origins). WAPE is 33.9% vs 29.1% for true seasonal naive, which makes the ML model's lift look larger than it is.
- **Passed:** weather is correctly excluded, because the stored values are realised weather, not forecasts issued at the time. Calendar/holiday features are known in advance. The rolling-origin split is clean and self-asserting.

## 4. Structural breaks

Nothing in any pipeline detects or adapts to a regime change: no change-point test, no sample weighting by recency, no trend/time-index feature, no drift monitor.

**Stress test:** I multiplied demand by 1.30 from 8 weeks before the cutoff onwards (for example, a new employer nearby, a competitor ATM closing, or a CRA vendor change shifting load).

| Model | Bias, baseline | Bias, after +30% shift |
| --- | --- | --- |
| Pure exogenous | +4.0% | **−18.7%** |
| Strategy B ⭐ | +3.2% | **−18.5%** |
| Strategy A | +5.4% | −15.8% |
| LightGBM censored | +1.9% | −20.2% |
| Strategy C | −6.9% | −7.5% |

Why:

- **Pure exogenous / B** learn each ATM's level from ~2 years of data. Eight weeks of new regime barely move a tree split, so the model keeps predicting the old level.
- **Strategy A** divides by the *full-history* median. That median is stale after a shift, and the stale denominator also feeds the ratio.
- **Strategy C** has 7- and 28-day rolling features, so it follows the new level. That is the only reason it survives. It has its own problem, though: it is trained on lags one day old, then served with features **frozen at the cutoff for 31 days** (`generate_portal_data.py:565-578`). That is train/serve skew.

Natural drift in the data is already non-trivial: year-on-year September growth ranges from −8.6% to +12.9% by ATM.

**Recommendations**

1. Make the target the **ratio to a trailing 28-day mean**, computed causally at the cutoff, and multiply back. This one change handles level shifts, scaling and cold start together.
2. Train with exponential **recency weights** (half-life of ~90 days).
3. Add a **CUSUM / rolling-bias monitor** per ATM: if the 14-day bias exceeds ±10%, flag the ATM and fall back to Strategy C.
4. Train Strategy C on rows that carry an explicit `horizon` and matching lag ages, as the rolling-origin script does.

## 5. Scaling and "exponential cash flows"

- **The premise doesn't hold in this data.** Daily demand runs from ₹37k to ₹26.6L with median ₹6.3L and **skew 0.89**. That is mildly right-skewed, not exponential, and there is no compounding trend.
- **Feature scaling is irrelevant to the model choice.** Gradient-boosted trees split on ranks, so the raw ₹ inputs are fine. The real risks are:
  - **No extrapolation.** A tree cannot predict above the largest leaf value it learned. If demand ever exceeds the historical range (growth, inflation, a mega-event), predictions are capped. The ratio-to-trailing-mean target (§4.1) fixes this.
  - **Pooled L1 in ₹ is dominated by the biggest ATMs.** Per-ATM WAPE ranges from 12.9% to 24.8%. The two low-volume branch ATMs (4, 8) get relatively little attention from the loss. Strategy A's ratio target is the right idea, but its denominator is stale.
  - **L1 predicts the median.** For right-skewed demand, the median sits below the mean, so the systematic risk is under-loading. That is acceptable only if the buffer layer adds back calibrated uncertainty, and it doesn't (below).
- **Intervals are miscalibrated.** σ is the **in-sample** residual std × √7 (`forecaster.py:172`, `generate_portal_data.py:841`). In-sample residuals understate out-of-sample error, and √7 assumes day-to-day errors are independent, which level-shift errors are not. A one-sided 99% bound on the 7-day total actually covers **95.7%**, so it fails ~4× as often as claimed. **Fix:** use quantile LightGBM (already built in `run_rolling_origin.py`), or conformal intervals from out-of-sample rolling-origin residuals on the 7-day sum.

## 6. Erratic / non-linear anomalies

What exists:

- `regression_l1` objective, which is robust to outliers in the target.
- Stockout "uncensoring" (`uncensoring.py:77-82`): `uncensored = demand / active_fraction`, with `active_fraction` floored at 0.20.

What's missing or wrong:

- **No anomaly handling at all:** no spike/outage flag, no winsorising, no separate treatment for fraud bursts, network outages, cassette jams or reject-bin events. All of these end up in the training target.
- **The uncensoring contradicts its own input.** `inventory_checkpoint_quality.csv` labels every row `inventory_checkpoints_only_not_downtime_or_unmet_demand`, yet `uncensoring.py` treats zero-balance snapshots as lost-demand time. It also assumes demand is spread evenly through the day, while real cash-outs cluster at evening peaks, so the correction is biased. The 0.20 floor permits up to a 5× inflation. In this data the effect is small (87 cash-out days, max multiplier 1.96×, 0.53% of volume), so the risk is in production, not here.
- **Spike audit:** 37 days have robust z > 4. **All are upward. 32 coincide with calendar events** (Diwali-pre, Ganesh, Dussehra, paydays, month-end) and are learnable, and the festival features cover them. **5 are unexplained**: ATMs 3, 6 (×2), 7, 8. One looks like Republic Day on a Sunday, which is not flagged as a regional holiday.
- **The data has no downward anomalies:** zero 0-demand days, zero incomplete-snapshot days. The simulator never generates outages, so nothing about the pipeline's behaviour under real failures has been tested.

**Recommendations**

1. Add a **downtime/outage mask**: exclude or down-weight those days from training rather than "uncensoring" them with a heuristic.
2. **Winsorise the training target** per ATM at robust-z ±5, *unless* the day is a flagged calendar event, so festival lift is still learned.
3. Use the **telemetry-derived downtime engine** (added in commit `c6386ba`) as the source of truth for censoring, instead of the zero-balance snapshot count.
4. Inject synthetic outages and fraud bursts into the simulator and re-run the backtest, so the anomaly path is actually tested.

## 7. Strategy B "zero-shot cold start"

Each `site_type` maps to exactly one ATM, and `capacity`/`cycle_days` are constant per ATM, so the site metadata works as `terminal_id` under another name. The 18.2% WAPE is measured on ATMs the model trained on.

**Leave-one-ATM-out test** (train on 7 ATMs, predict the unseen 8th):

| ATM | In-sample WAPE | Held-out WAPE | Held-out bias |
| --- | --- | --- | --- |
| 1 | 16.7% | 23.1% | −16.7% |
| 2 | 13.4% | 24.3% | +18.9% |
| 3 | 16.2% | 22.4% | +15.4% |
| 4 | 17.5% | 30.2% | +12.3% |
| 5 | 16.9% | **49.5%** | **+48.8%** |
| 6 | 24.8% | 24.2% | +6.4% |
| 7 | 20.1% | 29.1% | −21.3% |
| 8 | 22.5% | 31.0% | −3.1% |
| **All** | **18.2%** | **27.9%** | |

A genuinely new ATM should expect ~28% WAPE, with level errors of ±15–50%. Strategy A's "zero-retrain" label also needs the ATM's own training median, so it is not zero-shot either. With only 8 ATMs, one per site type, no site-type effect can be estimated; that requires a network-scale panel.

## 9. How to verify

After fixes 1, 4 and 6, the replenishment engine's WAPE should be about 17–18%, matching the rolling-origin LightGBM's 18.6%. One-sided 99% intervals should cover ≥98.5% of out-of-sample weeks. A leave-one-ATM-out run should be part of any cold-start claim.

### 10.1 Replenishment simulation

I re-ran `python3 -m replenishment_engine.run_simulation` (440 weekly cycles, 99% service target). I also ran the **pre-fix** forecaster on today's code to separate the causes:

| | Committed CSV (stale) | Pre-fix code, run today | After fix |
| --- | --- | --- | --- |
| Model 7-day WAPE (pure exogenous) | 7.7% | 7.7% | 9.0% |
| Naive 7-day WAPE | 27.0% | 27.0% | 18.9% |
| Stockout cycles (pure exogenous) | 9.6% | 30.5% | 31.1% |
| Savings vs naive | **18.1%** | 5.6% | **0.2%** |

What this means:

- **The committed 18% savings figure was already stale.** The same code run today gives 5.6% savings and ~31% stockouts. The CSV came from an earlier configuration. The likely cause: ATMs 1 and 7 have weekly demand of ₹61–77L but a ₹60L cassette cap in `config.py`, so they stock out almost every week whatever the forecast.
- **The fixes take it from 5.6% to ~0%.** Most of that comes from the honest baseline. Seasonal naive costs ₹2.5L less than the broken constant-naive did. The leak fix itself adds only ~₹0.4L to the model's cost.
- **On this data, the ML forecast currently saves nothing over "same weekday last week"** once the comparison is fair. The bottleneck is the replenishment policy (capacity and visit frequency at the high-volume ATMs), not forecast accuracy.

**Not yet synced:** `live_portal_v2/` and `UI_2/` keep their own copies of `portal_data.json`/`.js` and `model_*.txt`. They still show the old numbers. `live_portal_v2/` also has unrelated uncommitted edits, so it was left untouched.

**How to check:** `python3 tests/test_forecaster_leakage.py` prints `ok`. It poisons the test week with a huge value and fails if any model learns from it, and it fails on the pre-fix code.
